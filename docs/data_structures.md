# 数据结构报告素材

> 对应 AGENTS.md §10。每个结构给出：功能、实现要点、时间/空间复杂度、替代方案、选型理由、**实测耗时对比**。
> 实测口径：`time.perf_counter`，预热 3 轮、重复 7 次取中位、固定种子 42；复现命令 `python tools/bench_ds.py`，原始数据 `docs/bench_ds.json`，曲线 `docs/bench_ds.png`。

## 一、总览

| 数据结构 | 用途 | 复杂度 | 朴素替代 | 实测结论 |
|---|---|---|---|---|
| 定长数组环形缓冲 | 平滑器滑窗 / 最近 k 帧缓存 | 入队·出队·随机访问 $O(1)$，空间 $O(k)$ | `list.pop(0)`（$O(k)$） | 小 k 反而慢（Python 常数），k≥127 仍 0.63× |
| 滑窗 + 增量运行和 | 移动平均 | 单帧更新 $O(1)$ | 每次重算窗口和 $O(k)$ | k≥31 起加速 1.68–2.85× |

| `np.argpartition`（快速选择） | 角点响应取 Top-N | 平均 $O(N)$ | 全排序 $O(N\log N)$ | 稳定加速 8.8–11.1× |
| 向量化滑窗点积 | 高斯平滑 | 每帧 $O(k)$（常数远小于逐点循环） | 逐点 Python 循环 | 依赖 NumPy 广播，无逐点循环 |
| K-D 树（可选进阶） | 特征匹配加速 | 查询约 $O(\log N)$ | 暴力匹配 $O(N^2)$ | 未实现（LK 跟踪无需描述子匹配） |

## 二、逐项说明

### 1. 定长数组环形缓冲（`ds/ring_buffer.py`）

- **功能**：容量固定的 FIFO；写满后 `push` 自动驱逐最旧元素并返回它（滑窗语义）。
- **实现要点**：预分配定长列表 + 头指针 + 计数；写位置 `(head+count) % capacity`，全程不搬移元素。`__slots__` 降低开销。
- **复杂度**：push / popleft / `getitem` 均 $O(1)$，空间 $O(k)$。
- **替代**：`collections.deque(maxlen=k)`——红线 7 禁止用于主实现（仅允许测试对照）；`list.pop(0)` 为 $O(k)$ 搬移。
- **选型理由**：平滑器每帧一入一驱逐，需要 $O(1)$；手写下标的指针算术是课程要求。

**实测**（20000 次滑窗推进）：

| k | RingBuffer (ms) | list.pop(0) (ms) | 加速比 |
|---|---|---|---|
| 15 | 2.79 | 1.60 | 0.57× |
| 31 | 2.90 | 1.42 | 0.49× |
| 63 | 2.24 | 1.35 | 0.60× |
| 127 | 2.36 | 1.48 | 0.63× |
| 255 | 2.66 | 1.69 | 0.64× |

**诚实分析**：CPython 的 `list.pop(0)` 用 C 实现 `memmove`，k≤255 时搬移开销极小，而自研环形缓冲每次操作都有 Python 层属性访问与取模，常数劣势主导；随 k 增大两者差距收敛（0.49→0.64），符合“$O(1)$ vs $O(k)$ 渐进差异在小 k 被常数掩盖”的预期。报告中应同时给出**渐进复杂度**与**实测常数**两层结论，不能只报优势。

### 2. 滑窗 + 增量运行和（`src/smoothing.py` 移动平均）

- **功能**：窗口和增量维护（新值加入、被驱逐值减去），避免每次重算。
- **复杂度**：单帧 $O(1)$ vs 朴素 $O(k)$；空间 $O(k)$（复用环形缓冲）。
- **实测**（20000 帧序列）：

| k | 增量更新 (ms) | 每次重算 (ms) | 加速比 |
|---|---|---|---|
| 15 | 9.25 | 9.08 | 0.98× |
| 31 | 8.12 | 13.67 | **1.68×** |
| 63 | 8.70 | 14.75 | **1.70×** |
| 127 | 8.12 | 23.14 | **2.85×** |

k=15 时打平（窗口小、重算代价低），k≥31 后加速比随 k 单调上升——这正是 $O(1)$ 与 $O(k)$ 的分野，是报告里最有说服力的曲线。

### 3. 手写双堆 + 延迟删除（`src/smoothing.py` 中值平滑器）

- **功能**：维护滑窗中值（最大堆存下半区、最小堆存上半区，哈希表记录待删值）。
- **实现要点**：`push` 后按堆顶分类入堆并再平衡（$|sz_{lo}-sz_{hi}|\le1$）；驱逐时**延迟删除**（记入 `_deleted` 计数），元素升到堆顶才物理弹出。
  - 关键正确性细节：**必须先按干净堆顶分类，再清理**；反过来（先清理再分类）会把待删的堆顶移走，导致分类错判与空堆 `peek`。
- **复杂度**：更新 $O(\log k)$、查询中值 $O(1)$；空间 $O(k)$（延迟删除使物理堆略大）。
- **替代**：`heapq`（红线 7 禁用于主实现）；每次 `sorted()` 取中值 $O(k\log k)$。
- **实测**（5000 帧序列）：

| k | 双堆 (ms) | 每次排序 (ms) | 加速比 |
|---|---|---|---|
| 15 | 36.8 | 3.68 | 0.10× |
| 31 | 38.6 | 8.04 | 0.21× |
| 63 | 35.6 | 20.1 | 0.56× |
| 127 | 36.6 | 37.7 | **1.03×** |

**诚实分析**：`sorted()` 是 C 实现的 Timsort，小 k 时远快于纯 Python 的双堆（每次操作含函数调用、比较、字典维护）；k=127 时二者打平并开始反超，符合 $O(\log k)$ vs $O(k\log k)$ 的渐进关系。报告中应说明：**选用双堆是为了渐进复杂度与课程要求，且这是纯 Python 实现下的常数代价**，若改用 C 扩展或 `sorted` 在小窗口反而更快。

### 4. `np.argpartition` 取 Top-N（`src/features.py`）

- **功能**：从 N 个角点响应中取响应最大的 Top-N。
- **实现要点**：`np.argpartition(-resp, N-1)[:N]`（平均 $O(N)$），再对这 N 个候选排序保证输出稳定。
- **实测**：

| N | argpartition (ms) | 全排序 (ms) | 加速比 |
|---|---|---|---|
| 100 000 | 0.199 | 2.21 | **11.1×** |
| 500 000 | 1.97 | 17.4 | **8.8×** |
| 1 000 000 | 4.62 | 46.1 | **10.0×** |

稳定约一个数量级，是本项目最干净的一处复杂度收益。

### 5. 向量化滑窗点积（高斯平滑）

手写高斯核（$\sigma=$ window/6），与环形缓冲内容做点积；部分窗口按可得抽头重归一。全程 NumPy 广播，无逐点 Python 循环（红线 4 要求）。

### 6. K-D 树（可选，未实现）

流水线用 LK 跟踪建立逐帧对应，不需要描述子匹配，故 K-D 树无应用场景；保留为可选进阶项（§10 表格仍列出）。

## 四、给报告的结论模板

1. 渐进复杂度优势必须**配合实测曲线**呈现：环形缓冲与双堆在小窗口被 Python 常数掩盖，随 k 增大差距按预期拉开。
2. 增量窗口和与 `argpartition` 是本项目中收益明确的两处（1.7–2.9×、8.8–11.1×）。
3. 所有对照基准（`collections.deque`、`heapq`、`sorted`、cv2 系列）**仅出现在 tests/ 与 bench 中**，主实现全部手写（红线 7）。
